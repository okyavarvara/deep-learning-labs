# ЛР4. FP32 проти INT8: квантизація після навчання (ONNX Runtime)

Беремо модель із ЛР3 (ResNet-18, режим `frozen`, зерно 3), переводимо її у формат ONNX, будуємо з неї восьмибітну версію **статичною квантизацією після навчання** (post-training quantization) і відповідаємо на питання роботи:

* чи дає INT8 виграш у **затримці** на моєму CPU;
* **якою зміною якості** (macro-$F1$, accuracy, згода передбачень) і **розміру файлу** цей виграш купується;
* чи відрізняється зміна якості від шуму (парне порівняння на тих самих 1502 зображеннях test).

Оцінюється протокол вимірювання, а не конкретне прискорення. Усі вимірювання виконано на CPU ноутбука. Набір даних: [Intel Image Classification](https://www.kaggle.com/datasets/puneet6060/intel-image-classification) (`seg_train`, `seg_test`; самі зображення в репозиторій не додано).

## 2. Що саме реалізовано

**Модель.** `lab3_model.pt` завантажується через `torch.load(path, map_location="cpu", weights_only=True)`; будується `torchvision.models.resnet18(weights=None)`, `model.fc` замінюється на `Linear(512, 6)`, завантажується `state_dict`, модель переводиться в `eval()`. Порядок класів і `img_size` у файлі перевіряються: `buildings, forest, glacier, mountain, sea, street`, `img_size = 160`. У файлі записано режим **frozen**, зерно **3** (тобто саме та модель, що дала macro-$F1 = 0.8892$ на test у ЛР3).

**Дані й поділ.** Використовується `split.csv` з ЛР3 (SHA-256 `d3a611aec41f6e335ab58287f10a443f3e0e35aa9adfefae662d48b15af567f9`); validation не використовується. Перед роботою перевіряються кількість і сума числових імен файлів (`20057.jpg` $\to$ 20057) для двох частин.

**Перетворення входу** для всіх зображень (і калібрувальних, і тестових) таке саме, як для test у ЛР3: `Resize((160, 160))` $\to$ `ToTensor()` $\to$ `Normalize(mean, std)`, $\text{mean}=(0.485,\,0.456,\,0.406)$, $\text{std}=(0.229,\,0.224,\,0.225)$; зображення відкриваються через Pillow з `.convert("RGB")`. Порядок тестових зображень у всіх обчисленнях - як порядок рядків `test` у `split.csv`. Зображення підготовлено один раз у масив `float32` форми $1502\times3\times160\times160$.

**Фіксовані налаштування (з умови)**

| Етап | Налаштування |
|---|---|
| Експорт | `torch.onnx.export(..., dynamo=False, opset_version=17)`, вхід `input`, вихід `logits`, змінний розмір пакета (`dynamic_axes` за віссю 0), модель у `eval()` |
| Підготовка до квантизації | `quant_pre_process(fp32, prep, skip_symbolic_shape=True)` |
| Квантизація | `quantize_static` з `quant_format=QuantFormat.QDQ`, `activation_type=QuantType.QUInt8`, `weight_type=QuantType.QInt8`, `per_channel=True`, `calibrate_method=CalibrationMethod.MinMax`; решта аргументів за замовчуванням |
| Сесія | `onnxruntime.InferenceSession` з `providers=["CPUExecutionProvider"]`, `intra_op_num_threads=1`, `inter_op_num_threads=1`, рівень оптимізації графа за замовчуванням |
| Якість | усі 1502 зображення test, пакети по 64, порядок як у `split.csv` |
| Затримка | розмір пакета $B=1$, 1 потік, 3 раунди, у кожному 20 прогрівальних викликів і 100 вимірів на варіант |

**Метрики.** Для кожного класу $k$ розглядаємо його проти решти:

$$F1_k=\frac{2\,TP_k}{2\,TP_k+FP_k+FN_k},\qquad \text{macro-}F1=\frac{1}{6}\sum_{k=0}^{5}F1_k,\qquad \text{accuracy}=\frac{1}{n}\sum_{i=1}^{n}\mathbb{1}\left[\hat y_i=y_i\right],\; n=1502 .$$

Обчислення macro-$F1$ - `sklearn.metrics.f1_score(average="macro")`. **Згода передбачень** (prediction agreement) варіанта з FP32 - частка зображень, для яких він передбачає той самий клас, що й FP32:

$$\text{agreement}=\frac{1}{n}\sum_{i=1}^{n}\mathbb{1}\left[\hat y_i^{\text{INT8}}=\hat y_i^{\text{FP32}}\right].$$

## 3. Експорт і перевірка відповідності (п. 1)

Модель експортовано у `lab4_fp32.onnx` за 0.68 с. Для всіх 1502 зображень test обчислено логіти моделі PyTorch (під `torch.no_grad()`) і логіти сесії ONNX Runtime (пакети по 64, одні й ті самі пакети для обох).

| Величина | Значення | Контроль з умови |
|---|---|---|
| $\max\lvert z_{\text{ONNX}}-z_{\text{PyTorch}}\rvert$ | $1.335\cdot10^{-5}$ | порядку $10^{-5}$, має бути $<10^{-3}$ ✓ (в еталоні $5.25\cdot10^{-5}$) |
| частка зображень зі збігом argmax | 1.0000 | 1.0000 ✓ |
| macro-$F1$ PyTorch | 0.8892 | дорівнює числу на test у ЛР3 (0.8892) ✓ |
| macro-$F1$ ONNX FP32 | 0.8892 | те саме ✓ |
| вузлів `Conv` в експортованому графі | 20 | 20 ✓ |
| вузлів `BatchNormalization` | 0 | 0 ✓ |
| розмір `lab4_fp32.onnx` | 44 708 866 байт = 44.71 МБ | збігається з орієнтиром (44.71 МБ) |

ONNX-файл обчислює ту саму функцію, що й модель PyTorch: логіти відрізняються на $10^{-5}$ (це порядок похибки округлення `float32`, а не різниця функцій), класи збігаються на всіх зображеннях, а macro-$F1$ однаковий. Жодного `BatchNormalization` у графі немає, бо під час експорту в режимі `eval()` пакетну нормалізацію злито з попередньою згорткою (залишилося 20 згорток: `conv1`, 16 у блоках `layer1`-`layer4` і 3 згортки `downsample`). Число $1.335\cdot10^{-5}$ відрізняється від еталонного $5.25\cdot10^{-5}$: за умовою точні молодші розряди залежать від процесора й збірки, а вимога - лише $<10^{-3}$.

## 4. Калібрування й квантизація (п. 2)

### 4.1. Калібрувальна вибірка

200 зображень частини **train** поділу ЛР3:

1. беремо 1200 рядків `split.csv` з `part == "train"` і сортуємо їх за іменем файлу як рядки;
2. `idx = np.random.default_rng(0).permutation(1200)[:200]`; калібрувальні рядки мають номери `idx` у відсортованому списку.

| Контроль | Отримано | З умови |
|---|---|---|
| кількість | 200 | 200 ✓ |
| сума числових імен файлів | 1 921 470 | 1 921 470 ✓ |
| buildings / forest / glacier / mountain / sea / street | 40 / 35 / 36 / 33 / 29 / 27 | 40 / 35 / 36 / 33 / 29 / 27 ✓ |

Контроль поділу: train: 1200 зображень, сума імен 11 993 084; test: 1502 зображення, сума імен 33 351 444 - обидва збігаються з рядком «Разом» контрольної таблиці ЛР3.

**Чому калібрування береться з train, а не з test.** Діапазони активацій, оцінені калібруванням, стають частиною моделі (з них обчислюються масштаби квантизації), тобто це «навчання» параметрів INT8-моделі на цих зображеннях. Якби калібрувальні зображення були з test, то оцінка якості INT8 на test була б оптимістичною (модель «бачила» ці зображення), а test перестав би бути незалежним. Тому test для калібрування не використовується (правило з лекції 8).

### 4.2. Квантизація

Граф підготовлено `quant_pre_process(..., skip_symbolic_shape=True)` і квантизовано `quantize_static` із параметрами з таблиці фіксованих налаштувань (QDQ, активації `QUInt8`, ваги `QInt8`, `per_channel=True`, MinMax). Калібрувальні зображення подавались через `CalibrationDataReader` **по одному** ($1\times3\times160\times160$). Результат - `lab4_int8.onnx`.

## 5. Якість (п. 3)

Для FP32 і INT8 на всіх 1502 зображеннях test обчислено macro-$F1$, accuracy і згоду з FP32. Обидва варіанти оцінюються на **тих самих** зображеннях, тому порівнюємо їх **попарно**. Нехай $b$ - кількість зображень, на яких INT8 відповідає правильно, а FP32 помиляється, $c$ - кількість зображень із протилежною ситуацією. Якщо варіанти однаково точні, $b\sim\mathrm{Bin}(b+c,\,1/2)$, звідки

$$\Delta\mathrm{acc}=\mathrm{acc}_{\text{INT8}}-\mathrm{acc}_{\text{FP32}}=\frac{b-c}{n},\qquad \mathrm{SE}(\Delta\mathrm{acc})\approx\frac{\sqrt{b+c}}{n},\qquad n=1502 .$$

**Правило інтерпретації.** Якщо $\lvert b-c\rvert\le2\sqrt{b+c}$, різниця якості не відрізняється від шуму; якщо $\lvert b-c\rvert>2\sqrt{b+c}$ - відрізняється, і її напрям треба назвати.

| Варіант | macro-$F1$ | accuracy | Згода з FP32 | $b$ | $c$ | $\Delta\mathrm{acc}\pm\mathrm{SE}$ |
|---|---|---|---|---|---|---|
| FP32 | 0.8892 | 0.8862 | 1.0000 | 0 | 0 | +0.0000 |
| INT8 | 0.8900 | 0.8868 | 0.9920 | 6 | 5 | +0.0007 $\pm$ 0.0022 |

**Вердикт за правилом.** $\lvert b-c\rvert=\lvert 6-5\rvert=1$, $\;2\sqrt{b+c}=2\sqrt{11}=6.63$; $1\le6.63$ $\Rightarrow$ **різниця якості не відрізняється від шуму**. Напрям назвати не можна: $\Delta\mathrm{acc}=+0.0007$ - це $\approx0.3$ стандартної похибки, тобто один «зайвий» правильний відповідь із 1502.

**Що відбулося на рівні зображень.** Клас змінився на 12 зображеннях із 1502 (згода $=1-12/1502=0.9920$). З них: INT8 **виправила** 6 помилок FP32 ($b$), **зіпсувала** 5 правильних відповідей ($c$), а на 1 зображенні обидві відповіді хибні (FP32 і INT8 помиляються по-різному). Отже зміни передбачень відбуваються в обидва боки й майже компенсуються.

### Порівняння SE парної різниці зі стандартною похибкою однієї моделі

Стандартна похибка частки правильних відповідей однієї моделі з ЛР3:

$$\mathrm{SE}_1=\sqrt{\frac{p(1-p)}{n}}=\sqrt{\frac{0.8862\cdot0.1138}{1502}}=0.0082,$$

а похибка парної різниці $\mathrm{SE}(\Delta\mathrm{acc})=\sqrt{11}/1502=0.0022$, тобто **у 3.7 раза менша**. Причина: накладаючи моделі на ті самі зображення, ми порівнюємо їх лише там, де вони розходяться. На 1490 зображеннях із 1502 передбачення збігаються, тож вони однаково правильні або однаково хибні в обох варіантах і в різницю $b-c$ **нічого не вносять**. Невизначеність різниці визначається лише числом «розбіжних» зображень, $b+c=11$ (під коренем $11$), тоді як похибка однієї моделі визначається всіма зображеннями, які можуть бути і правильними, і хибними: $np(1-p)\approx151$ (під коренем $151$): $\sqrt{151/11}\approx3.7$. Чим більше моделі схожі (вища згода), тим менша парна похибка.

## 6. Дослід із потензорними вагами (п. 4)

Поканальна (per-channel) квантизація бере для кожного вихідного каналу $c$ власний діапазон $\alpha_c$, потензорна (per-tensor) - один діапазон $\max_{c}\alpha_c$ на весь тензор. Перехід до потензорних ваг коштує каналу $c$ приблизно

$$\log_2\frac{\max_{c'}\alpha_{c'}}{\alpha_c}\ \text{біта}$$

(канал із малим діапазоном отримує грубіший крок і втрачає розряди).

### 6.1. Діапазони каналів

Для кожного вузла `Conv` графа `lab4_fp32.onnx`: $\alpha_c=\max\lvert w\rvert$ за всіма елементами вихідного каналу $c$ (ваги беруться з `graph.initializer` через `onnx.numpy_helper.to_array` за іменем другого входу вузла, форма $(C_{out},C_{in},k_H,k_W)$), і відношення

$$r=\frac{\max_c\alpha_c}{\operatorname{median}_c\alpha_c}.$$

Три згортки з найбільшим $r$ і медіана $r$ за всіма 20 згортками:

| Згортка | $r$ | $\log_2 r$, біт |
|---|---|---|
| `/conv1/Conv` | 6.67 | 2.74 |
| `/layer3/layer3.1/conv2/Conv` | 5.90 | 2.56 |
| `/layer3/layer3.0/downsample/downsample.0/Conv` | 4.92 | 2.30 |
| **медіана $r$ за 20 згортками** | **3.44** | **1.78** |

Медіанному каналу потензорний крок коштує $\log_2 3.44=\mathbf{1.78}$ **біта** (з 8 лишається приблизно 6.2). Значення збігаються з орієнтиром із умови (6.67; 5.90; 4.92; 3.44; 1.78 біта). Для порівняння, у першій згортці MobileNetV3 з лекції 9 $r$ сягає 90 ($\log_2 90\approx6.5$ біта - майже весь байт). Повна таблиця за всіма згортками (з `lab4_results.json`):

### 6.2. Прогноз до запуску

Прогноз записано **до** побудови `lab4_int8_per_tensor.onnx`. Повний текст є в `run.py` як `PER_TENSOR_PREDICTION`, друкується в `lab4_log.txt` перед запуском досліду і збережений у `lab4_results.json`; нижче - його стислий переказ (після запуску прогноз не виправлявся):

> За $r$ з таблиці: медіанна згортка втрачає 1.78 біта (лишається ≈ 6.2 з 8), найгірша, `conv1`, - 2.74 біта. Це далеко від MobileNetV3 ($r\approx90$, ≈ 6.5 біта), тому катастрофи не очікую. **Згода передбачень з FP32 впаде** порівняно з per-channel INT8 (0.9920), бо кожне додаткове округлення зсуває логіти й перекидає найнепевніші зображення біля меж класів, але лишиться високою: оцінюю **0.97-0.99** (3-45 зображень із 1502 змінять клас), у всякому разі вище 0.95. **macro-$F1$ за правилом п. 3 не зміниться понад шум** ($\lvert b-c\rvert\le2\sqrt{b+c}$): зміни класу відбуваються в обидва боки (було правильно $\to$ стало неправильно і навпаки), тому $b$ і $c$ значною мірою компенсуються.

### 6.3. Запуск і зіставлення з прогнозом

Побудовано `lab4_int8_per_tensor.onnx` з `per_channel=False` на тій самій калібрувальній вибірці й з рештою тих самих параметрів (час `quantize_static` 6.21 с). Рядок таблиці п. 3 (затримку не міряли):

| Варіант | macro-$F1$ | accuracy | Згода з FP32 | $b$ | $c$ | $\Delta\mathrm{acc}\pm\mathrm{SE}$ |
|---|---|---|---|---|---|---|
| INT8 per-channel | 0.8900 | 0.8868 | 0.9920 | 6 | 5 | +0.0007 $\pm$ 0.0022 |
| INT8 per-tensor | 0.8931 | 0.8901 | 0.9794 | 18 | 12 | +0.0040 $\pm$ 0.0036 |

Для per-tensor: $\lvert b-c\rvert=6$, $2\sqrt{b+c}=2\sqrt{30}=10.95$; $6\le10.95$ $\Rightarrow$ різниця якості **не відрізняється від шуму**. Клас змінився на 31 зображенні ($1-31/1502=0.9794$): 18 виправлено, 12 зіпсовано, 1 - обидві хибні.

**Зіставлення з прогнозом - прогноз підтвердився:**

* згода впала з 0.9920 до **0.9794** (з 12 до 31 зміненого зображення), лишилась у прогнозованому інтервалі 0.97-0.99 і вище 0.95 ✓;
* змінилися 31 зображення, у прогнозованих межах 3-45 ✓;
* macro-$F1$ за правилом не змінився понад шум ($6\le10.95$) ✓. Формально macro-$F1$ навіть трохи вищий (0.8931 проти 0.8900), але це в межах шуму, і ми не вважаємо це покращенням;
* прогноз «$b$ і $c$ значною мірою компенсуються» - підтвердився частково: $b=18$, $c=12$, їхня різниця 6 - це мала частка від 30 розбіжних зображень.

### 6.4. Чому згода реагує на квантизацію чутливіше за macro-$F1$ і чому розходження компенсуються в $b-c$

* **Згода** рахує **будь-яку** зміну передбаченого класу, у тому числі коли правильна відповідь перетворюється на хибну, і навпаки. **macro-$F1$ й accuracy** рахують лише **правильність**: виправлене зображення додає $+1$ до числа правильних, зіпсоване - $-1$. Тому кожна зміна класу зменшує згоду на $1/n$, але змінює accuracy лише тоді, коли в підсумку змінюється правильність.
* Квантизація зсуває логіти на малу величину, тож переходять межу класів лише ті зображення, для яких два найбільші логіти були майже рівні (найнепевніші). Таке зображення з приблизно рівною ймовірністю перескакує і з правильного класу на хибний, і з хибного на правильний, оскільки обидва класи для моделі однаково правдоподібні. Тому $b$ і $c$ мають приблизно однаковий розмір, і їхня різниця $b-c$ (яка й визначає accuracy) - це різниця двох близьких чисел, значно менша за $b+c$; шум $\sqrt{b+c}$ співмірний із нею. Звідси: згода змінилася помітно (0.9920 $\to$ 0.9794), а $b-c$ - від 1 до 6 зображень, у межах шуму.

## 7. Затримка (п. 5)

Затримка вимірюється для `lab4_fp32.onnx` і `lab4_int8.onnx` за протоколом з умови:

1. Обидві сесії створюються заздалегідь (створення сесії, експорт і квантизація в час не входять).
2. Вхід один і той самий - перше зображення test у порядку `split.csv`, масив `float32` форми $1\times3\times160\times160$, підготовлений до вимірювання.

4. Вимір містить один виклик `sess.run` між двома зчитуваннями `time.perf_counter()`, і нічого більше.

Ноутбук під час вимірювання був підключений до живлення, важкі програми закриті. Розмір файлу - кількість байтів, поділена на $10^6$. Прискорення визначається як $p_{50}^{\text{FP32}}/p_{50}^{\text{INT8}}$.

| Варіант | Файл, МБ | $p_{50}$, мс | $p_{95}$, мс | $p_{50}$ за раундами, мс |
|---|---|---|---|---|
| FP32 | 44.71 | 20.509 | 22.806 | 20.577, 20.523, 20.384 |
| INT8 | 11.30 | 6.773 | 7.842 | 6.814, 6.829, 6.695 |

| Відношення FP32 / INT8 | Значення |
|---|---|
| розмір файлу | 3.96 $\times$ |
| $p_{50}$ (прискорення) | **3.03 $\times$** |
| $p_{95}$ | 2.91 $\times$ |

**Правило інтерпретації.** Зміну затримки вважаємо виміряною, якщо відрізки $[\min,\max]$ значень $p_{50}$ за раундами для двох варіантів не перетинаються. FP32: $[20.384;\ 20.577]$; INT8: $[6.695;\ 6.829]$. Відрізки не перетинаються (найповільніший раунд INT8, 6.829 мс, майже втричі швидший за найшвидший раунд FP32, 20.384 мс) $\Rightarrow$ **зміна затримки виміряна**. Розкид $p_{50}$ між раундами малий (≈ 1 % для FP32 і ≈ 2 % для INT8), тобто прискорення стійке.

Розподіл має правий «хвіст»: мінімум FP32 - 19.83 мс, максимум - 31.75 мс, середнє - 20.85 мс (трохи вище за $p_{50}=20.51$); для INT8 мінімум 6.34, максимум 12.71, середнє 6.95 мс (при $p_{50}=6.77$). Тому в таблиці наведено $p_{50}$ і $p_{95}$, а не середнє: поодинокі викиди (імовірно, переривання ОС, планувальник, перемикання між ядрами) тягнуть середнє вгору, а медіана й 95-й перцентиль описують типовий виклик і «поганий, але не екстремальний» виклик.

## 8. Висновок (п. 6)

Висновок стосується **конкретного процесора** (Intel Core i7-13620H, 1 потік, $B=1$) і **конкретної версії ONNX Runtime** (1.29.0).

**1. Зміна ресурсів.** Файл зменшився у **3.96 раза** (44.71 МБ $\to$ 11.30 МБ), $p_{50}$ - у **3.03 раза** (20.509 мс $\to$ 6.773 мс), $p_{95}$ - у **2.91 раза** (22.806 мс $\to$ 7.842 мс). Зміна затримки **виміряна** за правилом п. 5: відрізки $p_{50}$ за раундами $[20.384;\,20.577]$ мс (FP32) і $[6.695;\,6.829]$ мс (INT8) не перетинаються.

**2. Якість відносно шуму.** Різниця якості **не відрізняється від шуму**: $\lvert b-c\rvert=1\le2\sqrt{b+c}=6.63$; $\Delta\mathrm{acc}=+0.0007\pm0.0022$, macro-$F1$ 0.8900 проти 0.8892. **Згода передбачень з FP32 - 0.9920**: клас змінився на 12 зображеннях із 1502 (6 виправлено, 5 зіпсовано, 1 - обидві відповіді хибні).

**3. Чому прискорення (3.03) менше за чотирикратне зменшення байтів ваг (3.96).** Спираюсь на модель даху (roofline): час виконання обмежений більшим із двох часів - обчислень і руху даних,

$$T\ \gtrsim\ \max\left(\frac{W}{P},\ \frac{Q}{B}\right),$$

де $W$ - кількість операцій, $P$ - пікова продуктивність обчислень, $Q$ - кількість байтів, що рухаються між пам'яттю й процесором, $B$ - пропускна здатність пам'яті. Квантизація зменшує $Q$ приблизно в чотири рази (файл у 3.96 раза менший; не рівно в 4 - через масштаби, нульові точки та вузли Quantize/Dequantize в графі), тож *якби* виконання було обмежене пам'яттю ($Q/B$), прискорення дорівнювало б майже 4. Але на цій задачі вузьким місцем є **обчислення**: ResNet-18 на вході $160\times160$ має $\approx9.25\cdot10^{8}$ множень-додавань, а ваги FP32 займають 44.7 МБ, тобто **арифметична інтенсивність** близько $2\cdot9.25\cdot10^{8}/4.47\cdot10^{7}\approx41$ операцій на байт ваг, а для INT8 - близько 164. Фактичний потік ваг при $p_{50}=20.5$ мс - лише $44.71/0.0205\approx2.2$ ГБ/с, що на порядок менше за пропускну здатність пам'яті звичайного ноутбука (десятки ГБ/с; це довідкова оцінка, її я не вимірювала). Отже навіть FP32-модель не впирається в пам'ять, а чотириразове зменшення байтів само по собі прискорення не дає: **прискорення визначається відношенням пропускної здатності цілочисельних і `float32`-ядер** (скільки множень-додавань на такт робить INT8-ядро порівняно з FMA над `float32`), а не відношенням байтів. Виміряно: FP32 - $\approx45$ ГМАС/с, INT8 - $\approx137$ ГМАС/с на одному потоці, тобто цілочисельні ядра дають приблизно потрійний виграш за обчисленнями. Ще дві імовірні причини, чому не 4 (їх я окремо не вимірювала): (а) частина графа лишається в `float32`, а вузли Quantize/Dequantize (QDQ) - поелементні операції, обмежені пам'яттю, які не прискорюються; (б) накладні витрати сесії на один виклик, що однакові для обох варіантів і «розбавляють» відношення.

**Чи має мій CPU цілочисельні ядра для INT8.** Так: AVX2 (256-розрядні цілочисельні інструкції) на цьому процесорі є, і саме вони дають виграш; AVX-512 немає. Виграш у 3.03 раза показує, що ядра INT8 ONNX Runtime на цьому CPU ефективні. На процесорі без швидких цілочисельних інструкцій (або на x86 без VNNI, де множення $u8\times s8$ іде через проміжні 16-розрядні суми з можливим насиченням) прискорення могло б бути значно меншим, а якість INT8 - нижчою; я цього не перевіряла, а в нашому запуску погіршення якості немає (згода 0.9920). Для порівняння: на Apple M3 Pro (з умови) - 3.91 раза; мій x86-ноутбук дав 3.03.

**4. Чи придатна INT8-модель для цієї задачі на моєму ноутбуці.** **Так, придатна.** Якість у межах шуму (різниця одне зображення з 1502, 99.2 % збігів з FP32), розмір менший у 3.96 раза, виміряне прискорення 3.03 раза за $p_{50}$ і 2.91 раза за $p_{95}$ (запас по хвостових затримках зберігається). Обмеження висновку: тестова вибірка скінченна ($n=1502$, SE однієї моделі $\approx0.008$), затримку виміряно на одному вході, на одному потоці й одному процесорі; на іншому CPU чи іншій версії ONNX Runtime число прискорення й, можливо, якість будуть іншими. Потензорні ваги (п. 4) якість теж не зруйнували (згода 0.9794), тож для цієї мережі запас по бітах ваг великий, але саме per-channel лишає найвищу згоду з FP32.

Використано для: прочитання умови лабораторної; написання коду; перевірки конвеєра на синтетичних даних і діагностики помилки квантизації на Windows (кирилиця в шляху); чернетки цього README (структура, таблиці, формули в LaTeX, пояснення).
* **Хто що виконував.** Код і чернетку звіту підготовлено за допомогою Claude. Остаточний запуск, на якому засновані всі числа README, виконано мною на власному ноутбуці командою з §1; Claude лише зчитав `lab4_results.json` / `lab4_log.txt` / `lab4_tables.md` і переніс числа в текст.
* Я відповідаю за розуміння поданого розв'язку і можу пояснити код, перевірки та числа на захисті. Тексти пояснень у §5-§8 слід читати як чернетку, яку потрібно перевірити та за потреби переформулювати власними словами. Довідкові оцінки в §8 (пропускна здатність пам'яті ноутбука; відсутність AVX-512 за сторінкою Intel) не виміряні мною і позначені як оцінки.
* **Зовнішнє програмне забезпечення:** PyTorch, torchvision (ResNet-18), ONNX, ONNX Runtime (`quantize_static`, `quant_pre_process`), NumPy, scikit-learn (`f1_score`), Pillow, py-cpuinfo, `uv`.
